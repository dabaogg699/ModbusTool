# ModbusTool 下一阶段优化摘要
## 一、现状复盘
当前版本已完成核心功能闭环：Modbus TCP/RTU主站通信、寄存器读写、轮询、报文监视、点位CSV导入导出、基础工作区保存；单元测试全部通过，构建无报错。
现存明确问题 + 业务短板：
1. UI：主题切换失效、配色单一、部分控件/数据渲染重叠、DPI高缩放下布局兼容性隐患
2. 对标缺失：界面布局、点位管理、批量配置逻辑距离 Modbus Poll 的易用性差距较大
3. 多站并发限制：当前单实例仅单主站会话，**不支持多实例/多主站并行独立测试**（你后续需要同时调试多个从站、多套PLC程序）
4. 配置导入导出：已有基础CSV，但缺少工作区快照、模板复用、点位分组、批量修改功能

> 核心目标：保留现有全部通信底层逻辑（ModbusCore、Master/Slave协议库不动），只迭代UI层、会话管理层、配置管理层、样式主题层，对齐Modbus Poll使用习惯，同时支持多开独立主站。

## 二、分模块详细优化清单
### （一）UI布局 & 交互（对标 Modbus Poll，优先修复重叠、布局错乱）
1. **布局重构**
    - 拆分页面区域为固定分区：【会话&从站列表区】【点位表格主视图】【右侧通信参数面板】【底部报文监视器】，使用Grid+DockPanel严格约束布局，消除数据单元格、面板控件重叠问题；高DPI（125%/150%/175%）适配验证
    - 点位表格参考Modbus Poll：表头支持自定义列开关（地址、十六进制、数值、原始HEX、数据类型、字节序、更新时间、状态、备注），支持拖拽调整列宽、列排序、冻结首列
    - 表格单元格：区分只读/可写入单元格，双击写入逻辑对齐老版本工具，支持十进制/0x十六进制输入提示
2. **主题系统修复 + 配色扩展（重点解决当前主题切换失效）**
    - 修复主题切换绑定逻辑：区分 浅色/深色/工业蓝/深灰工业风 4套内置主题，切换时全局资源字典重载，所有控件、表格、日志、输入框统一刷新样式，不再出现局部样式残留
    - 配色体系：区分状态色（正常更新绿色、超时灰色、报错红色、未查询浅灰），表格行交替底色，报文收发区分方向颜色（发送：蓝色，接收：绿色，异常报文：红色）
    - 预留自定义配色入口：允许导出/导入主题json，方便工控现场统一风格
3. **交互细节对齐Modbus Poll**
    - 点位支持分组：按设备/功能码分组折叠，分组批量启用/禁用轮询
    - 表格右键菜单：批量添加、批量删除、复制点位、写入值、重置、导出选中点位、快速修改字节序/数据类型
    - 历史趋势页：支持多选点位同时绘图，坐标轴自适应、曲线配色区分，支持暂停、快照、导出图片

### （二）配置导入导出 & 工作区能力增强
1. CSV点位导入导出升级
    - 兼容老版MBScan原有CSV格式，**双向兼容**，老工程文件直接导入不丢数据
    - 导入时增加校验弹窗：地址重复、非法地址、超出寄存器范围、功能码冲突校验，支持自动跳过/覆盖/终止三种策略
    - 导出支持两种模式：全部点位 / 选中点位，可选择是否携带备注、轮询周期、数据类型、字节序配置
2. 工作区（Workspace）增强
    - 工作区文件保存：包含**完整会话参数、从站列表、点位表、轮询周期、超时重试参数、日志过滤配置**，打开后一键恢复全部环境
    - 工作区模板：另存为模板，新建会话直接加载模板，不用重复配置串口、波特率、超时参数
    - 支持单独导出/导入【从站配置模板】，批量复用同一套从站参数

### （三）多站并行测试能力（核心需求：同时调试多个从站、多套PLC）
两个方案同时落地，兼顾两种使用场景：
1. **方案A：单程序内多标签页多主站会话（推荐优先做）**
    - 顶部增加Tab标签：每一个Tab = 独立主站会话（独立串口/独立TCP连接、独立从站列表、独立点位表、独立轮询任务、独立报文日志）
    - 会话隔离：每个Tab的通信实例、轮询定时器、报文缓存完全隔离，互不干扰；一个站通信超时、断连，不会影响其他Tab的轮询
    - Tab支持命名、关闭、复制会话（复制当前Tab全部配置，快速新建同参数测试站）
2. **方案B：支持程序多开（独立进程）**
    - 修复单实例锁限制：默认允许多开程序，每个进程是一套完整Modbus主站；适合极端场景：多个不同COM串口同时占用、需要分开保存日志文件、分开录报文
    - 增加启动参数：支持命令行加载指定工作区文件，方便批量脚本拉起多个测试会话

> 说明：Tab内多会话优先开发，多开作为补充；串口资源本身系统限制，同一个COM口不能多会话占用，界面增加提示。

### （四）通信、轮询、日志 & 报文监视优化
1. 从站管理增强
    - 从站列表支持批量修改站号、周期、启用状态；支持拖拽排序轮询顺序
    - 轮询策略：支持按从站单独配置周期，不再全局统一周期；支持错开轮询时间，降低总线冲突（485 RTU场景非常实用）
2. 报文监视器升级
    - 报文列表增加筛选器：按站号、功能码、收发方向过滤
    - 报文支持高亮异常帧、CRC错误标记；支持保存报文日志到文本，带时间戳
    - 支持暂停捕获、清空、单独复制单条报文
3. 重试、超时可视化
    - 实时统计面板增加：各从站成功率、丢包计数、平均响应耗时，用状态指示灯直观展示通信健康度

### （五）遗留缺陷修复
- 修复主题切换不生效：排查WPF资源字典动态加载、DataTemplate、控件样式绑定问题，切换主题后所有窗口、用户控件同步刷新
- 修复界面数据重叠：约束ScrollViewer、Grid行列宽高，禁止控件自动溢出；表格容器自适应，大量点位时滚动区域独立
- 修复高DPI缩放错位：统一使用WPF独立DPI渲染，禁用WinForms混合模式缩放bug

### （六）附加扩展（可选，排期后置）
1. 支持点位备注、自定义标签，方便IO点表对齐PLC图纸
2. 导出点位表直接生成PLC注释表（适配西门子/汇川点表格式）
3. 内置字节序预设（ABCD/CDAB/BADC/DCBA），一键切换，对齐常用工控设备
4. 日志自动按时间分片保存，避免单日志文件过大

## 三、开发实施顺序建议（迭代优先级）
1. 第一优先级（紧急修复）：布局整改、消除控件重叠、修复主题切换逻辑、完善4套内置主题配色
2. 第二优先级（核心业务）：Tab多会话隔离架构、单程序多主站，会话之间通信隔离
3. 第三优先级：CSV兼容老格式、工作区模板、右键批量操作，对标Modbus Poll表格交互
4. 第四优先级：报文监视器增强、通信健康统计、多进程多开支持
5. 第五优先级：趋势曲线优化、点位分组、附加导出功能

## 四、边界约定（不改动范围，避免返工）
✅ 底层 ModbusCore 协议解析、RTU/TCP收发、CRC校验、寄存器读写核心库**保持不动**，只做上层UI、会话管理、配置层改造
✅ 原有全部功能（写入、手动命令、历史趋势、工作区保存）全部保留，不删减
✅ MBSlave从站模拟器部分同步配套适配主题，保持主从站视觉统一

## 五、验收标准
1. 主题切换：浅色/深色/工业主题一键切换，全界面样式同步，无残留、无错乱
2. 布局：100%~175% DPI缩放，表格、面板、日志无重叠、无溢出
3. 多会话：Tab多站独立轮询，A站断连不影响B站；支持复制会话、单独保存每个Tab工作区
4. 导入导出：兼容老MBScan CSV，导入校验完善，可导出选中点位
5. 交互：表格、右键菜单、点位编辑操作逻辑贴近Modbus Poll，降低学习成本
6. 多开：可独立启动多个程序进程，适合多串口并行测试

## 十一、双独立 EXE 与界面优化（2026-11-17）

### 11.1 双独立 exe 打包方案

**拆分原则**
- 协议与通信层完全复用：`ModbusCore`、`ModbusMaster`、`ModbusSlave` 代码零改动；`ModbusCore` 无 diff。
- `ModbusTool.App` 由单入口程序调整为共享 WPF UI 库（Views / ViewModels / Controls / Themes / Services），不再生成 exe。
- 新增两个独立 WPF 启动项目，UI 层相互隔离：
  - `src/ModbusMasterApp` → 程序集/可执行文件 `ModbusMaster`，窗口只装载 `MasterSessionsView` 与 `AboutView`。
  - `src/ModbusSlaveApp` → 程序集/可执行文件 `ModbusSlave`，窗口只装载 `SlaveView` 与 `AboutView`。
- 解决程序集简单名冲突：类库 `ModbusMaster` / `ModbusSlave` 的 AssemblyName 改为 `ModbusMaster.Core` / `ModbusSlave.Core`，命名空间与全部源码保持不变。
- 两个入口共用 `AppHost` 完成日志、全局异常兜底与命令行工作区解析；共用 `ThemeSelector` 完成四套主题切换与 JSON 导入导出。

**打包脚本逻辑（`scripts/publish.ps1`）**
1. 参数：`-Version`、`-Runtime`（默认 `win-x64`）、`-OutputDirectory`（默认 `artifacts`）、`-DotnetPath`、`-NoZip`。
2. 清空并重建 `artifacts\MBScan`、`artifacts\MBSlave`。
3. 分别对两个入口执行 `dotnet publish -c Release --self-contained true -p:Version=<版本> -p:BuildTime=<构建时间>`，非单文件，保留依赖 dll。
4. 生成 `ModbusMaster.exe.config` / `ModbusSlave.exe.config`（产品名、版本、构建时间）。
5. 解析 `Themes/*.xaml` 中的 Color 定义，自动生成四套主题 JSON 模板到 `MBScan\themes`，保证模板与内置主题同步。
6. 复制 `MBSlave/data.bin` 到 `MBSlave`；生成可编辑的 `about.json` 模板。
7. 默认额外生成 `ModbusMaster-<版本>-<RID>.zip` 与 `ModbusSlave-<版本>-<RID>.zip`；`-NoZip` 可跳过。

## 十三、UI 架构重构：侧边导航 + 单主内容区（2026-11-18）

### 13.1 放弃原三栏布局的原因

## 十五、批次 G8：报文跨线程修复 / 表格字段 / 日志开关 / 打包与图标（2026-11-19）

### 15.1 报文监视器无实时数据的根因与修复（P0 Bug）

**现象**：通信统计正常增长，但报文监视器列表始终为空，且无任何异常提示。

**根因**：`PacketMonitor.AddFrame` 由后台通信线程直接调用，内部读取了 WPF 依赖属性 `IsTcp`、`AutoDetect`、`MaxEntries`。WPF 依赖属性具有线程亲和性，跨线程访问会抛 `InvalidOperationException`；该异常被 `MasterService.OnTransportFrameSent` 的外层 try/catch 静默吞掉，导致报文入队从未执行。静态代码看似“管道已接通”，运行时实际断在 UI 层跨线程访问。

**修复**（仅 UI 层，`ModbusCore` 零改动）：
1. 在 `PacketMonitor` 内新增普通字段 `_isTcpMode`、`_autoDetectMode`、`_maxEntries`；
2. 通信线程只读取这些普通字段，禁止访问任何依赖属性；
3. 为 `IsTcp` / `AutoDetect` / `MaxEntries` 注册依赖属性变更回调，在 UI 线程同步刷新缓存字段；
4. 入队仍写入 `ConcurrentQueue`，由 200ms `DispatcherTimer` 批量刷入 UI，通信线程不直接操作控件。

**验证**：真实 TCP 主从回环，24 次完整交换后报文监视器收到 48 条帧（24 发送 + 24 接收）；方向、站号、功能码、毫秒时间戳、长度、原始 Hex 全部正确；暂停期间新报文不写入缓存。

### 15.2 寄存器表格字段调整

- 新增“二进制”列：16 位寄存器按 4 位分组（如 `0001 0010 0011 0100`），线圈/离散输入显示 `1`/`0`，使用等宽字体。
- “字符串”列默认隐藏，可通过工具栏“显示列”手动调出。
- 主站与从站共 9 处行数据填充点同步计算 `BinaryValue`，值刷新时二进制同步刷新；筛选也纳入二进制内容。

### 15.3 报文与日志的空态和级别控制

### 16.8 趋势曲线不显示修复（1.1.1，2026-11-20）

**现象**：主站正常轮询、报文与寄存器刷新正常，但历史趋势页始终显示“暂无数据”，图例存在却没有任何曲线。

**复现**：连接本地 `127.0.0.1:502`、站号 1 的从站，配置 10 个保持寄存器点位（勾选曲线）并 250ms 轮询，同时每 250ms 写入变化值。结果：`TrendService` 已记录 55 个样本，但 `TrendChart` 内部点数为 0，空态仍然显示。

**根因**：采样事件由通信线程触发，`MasterTrendView` 收到后调用 `TrendChart.Enqueue`，而该方法读取了 WPF 控件 `PauseButton.IsChecked`。依赖对象有线程亲和性，跨线程访问抛 `InvalidOperationException`；该异常一路传回 `MasterService.RecordHistory` 的 `catch { }` 被静默吞掉，于是每个样本都“记录成功但推送失败”。与 G8 报文监视器属于同一类跨线程缺陷。

**修复**：
1. `TrendChart` 新增普通字段 `_isPaused`，`Enqueue` 只读取该字段，通信线程不再触碰任何 WPF 控件；暂停状态由按钮的 Checked/Unchecked（UI 线程）写入。
2. `OnRefreshTick` 整体加 try/catch，渲染或数据异常只记录日志，不中断后续刷新。
3. `MasterViewModel.OnTrendSampleRecorded` 对订阅方调用加 try/catch，并按“首次失败”记录日志，避免高频刷屏；订阅方异常不再影响轮询与历史记录。
4. 保留 `_autoScale` 修复：初始化显式置为 `true`。

**验证**：同一真实从站场景下，12 秒内 10 条曲线收到 259 个采样点，X 轴为真实系统时间，空态自动隐藏，截图 `.screenshots/layout/43-trend-live.png`。

## 十九、主从站数据模拟与趋势异常专项排查（2026-11-20 晚）

### 19.1 异常现象（来自用户截图）

1. 历史趋势页 10 条曲线**全部呈同一种土黄色**，图例色块同样全部同色。
2. 趋势 X 轴与十字准星显示 **13:24:xx**，而本机系统时间为 **21:24:xx**，相差 8 小时。
3. 部分点位（4、5、8）读数为 0，曲线贴近底部几乎不可见；恒定值点位的曲线长时间不延伸。

### 19.2 链路逐环结论

| 环节 | 位置 | 结论 |
|---|---|---|
| 从站仿真 | `SimulationService.SimulateDataOnce` | 按 `width = GetRegisterCount(DataType)` 步进解码→递增/随机→回写，逻辑正确；地址 0 与其他寄存器初值不同导致相位差，非缺陷 |
| 采集/解析 | `MasterService.DecodePointValues` | `AddressOffset + DataType + ByteOrder + Scale/Offset` 解析正确；时间戳取 `DateTimeOffset.UtcNow`（UTC） |
| 历史存储 | `TrendService.Record` | 同值采样直接丢弃且无心跳点，导致恒值曲线停滞 |
| 视图同步 | `MasterTrendView.RebuildTrendSeries` | 对每个已存在点位**先 RemoveSeries 再 AddSeries**，是撞色直接诱因 |
| 图表渲染 | `TrendChart.AddSeries / ToPoint` | 调色板索引用 `_series.Count`；X 坐标用 `UtcDateTime.ToOADate()`，两处均为根因 |

### 19.3 根因分析

**Bug 1（P0）曲线全同色**
- 触发条件：任何 `TrendSeriesChanged`（点位增删改、启动轮询时的 `ResetTrendService`、分组批量开关、工作区重载）。
- 机理：`RebuildTrendSeries` 先删再建；`AddSeries` 以 `_series.Count` 作为调色板索引。10 条曲线时每次删除后 Count 恒为 9，所有点位都拿到索引 9，`PaletteHex[9 % 6 = 3] = #D97706`（橙/土黄），与截图完全一致。
- 附带损害：图例隐藏状态被重置、未保存的样式被覆盖、全量重建闪烁。

**Bug 2（P0）时间轴为 UTC**
- `TrendChart.ToPoint` 使用 `Timestamp.UtcDateTime.ToOADate()`，X 轴刻度与 `DateTime.FromOADate` 的十字准星均未做本地转换；而 CSV 导出（`MasterViewModel.ExportHistoryAsync`）使用 `ToLocalTime()`，导致图表与导出 CSV 时间口径不一致。
- 位置：`Controls/TrendChart.xaml.cs` `ToPoint`。

**Bug 3（P1）恒值曲线停滞**
- `TrendService.TrendSeries.TryAddValue` 在同值时直接返回 false，没有任何心跳采样；恒定值点位只有首点，无法成线，时间轴也不随系统时间推进。

### 19.4 修复内容

| 文件 | 修改 |
|---|---|
| `Controls/TrendChart.xaml.cs` | 调色板索引改为**最小空闲索引**，删除重建不再撞色；`ToPoint` 改用 `LocalDateTime.ToOADate()` |
| `Views/MasterTrendView.xaml.cs` | 重建时不再 Remove/Add，保留系列状态；样式应用与快照刷新语义不变（趋势服务重置后曲线照常清空） |
| `ModbusMaster/TrendService/TrendService.cs` | 增加 **2 秒心跳**：同值但距上次记录 ≥2s 仍补点，恒值曲线持续延伸，原有压缩策略与既有测试保持兼容 |
| `tests/ModbusMaster.Tests/WorkspaceAndTrendTests.cs` | 新增 `TrendEmitsHeartbeatForUnchangedValues` 覆盖心跳行为 |

### 19.5 验证结果

- Release 构建 0 警告 0 错误，单元测试 **101 项全部通过**（新增心跳 1 项）。

## 十七、版本发布管理规范（2026-11-20）

### 17.1 版本号唯一来源

| 文件 | 职责 |
|---|---|
| `version.json` | **唯一版本源**：`current` 为待发布版本，`released` 为已发布历史（版本、日期、变更类型、摘要） |
| `Directory.Build.props` | 开发构建使用的 `<Version>`，由脚本同步，必须与 `version.json` 一致 |
| `CHANGELOG.md` | 面向用户的变更日志，必须存在与 `current` 对应的 `## [x.y.z]` 小节 |
| `scripts/version.ps1` | 展示、提升、同步、校验版本 |
| `scripts/version-lib.ps1` | 版本解析与校验的共享实现，由两个脚本点源引用 |

约定：**任何 csproj 内禁止再写 `<Version>`**，避免覆盖统一版本导致漂移；发布前置检查会扫描 `src/**/*.csproj` 并拦截。

### 17.2 语义化版本与变更类型对应

| 变更类型 | 版本段 | 示例 | 适用场景 |
|---|---|---|---|
| 破坏性变更 | MAJOR | 1.1.0 → 2.0.0 | 工作区/配置格式不兼容、移除既有能力、程序拆分 |
| 功能新增 / 较大优化 | MINOR | 1.0.0 → 1.1.0 | 新增页面、替换组件、新增持久化能力 |
| 问题修复 / 细节调整 | PATCH | 1.1.0 → 1.1.1 | Bug 修复、样式微调、文案修正 |

提升命令（自动更新 `version.json`、`Directory.Build.props` 并插入 CHANGELOG 小节）：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\version.ps1 -Command bump -Part minor -Summary "变更摘要"
powershell -ExecutionPolicy Bypass -File scripts\version.ps1 -Command show
powershell -ExecutionPolicy Bypass -File scripts\version.ps1 -Command validate
powershell -ExecutionPolicy Bypass -File scripts\version.ps1 -Command sync
```

### 17.3 发布前置校验（不通过则中止）

`scripts/publish.ps1` 在调用 `dotnet publish` 前依次校验：

1. 版本号符合 SemVer（`MAJOR.MINOR.PATCH[-prerelease][+build]`），非法格式直接失败；
2. 版本未出现在 `released` 中，**禁止重复发布同一版本**；
3. 版本必须大于所有已发布版本（单调递增）；
4. 命令行 `-Version` 若提供，必须与 `version.json` 的 `current` 完全一致；
5. `Directory.Build.props` 的 `<Version>` 与 `current` 一致；
6. `CHANGELOG.md` 存在对应 `## [x.y.z]` 小节；
7. `src` 下所有 csproj 不含 `<Version>` 覆盖。

校验通过后才执行自包含发布；发布成功后自动向 `version.json` 的 `released` 写入记录（版本、日期、按差异推断的变更类型、摘要），实现版本号与发布日志一一对应。

### 17.6 使用流程

1. 开发完成后按变更类型执行 `version.ps1 -Command bump`；
2. 补全 `CHANGELOG.md` 中该版本条目；
3. 执行 `version.ps1 -Command validate` 确认“发布就绪: YES”；
4. 执行 `scripts/publish.ps1`（无需再传版本号，读取 `version.json`）；
5. 发布完成后检查 `version.json` 是否新增记录。
